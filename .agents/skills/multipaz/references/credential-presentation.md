# Credential Presentation

## Use this when

- implementing wallet presentment
- building consent and presentment-source logic
- adding QR, BLE, browser, or Digital Credentials entry points

## Current supported sample paths

- Shared consent and request handling: `samples/testapp/src/commonMain/kotlin/org/multipaz/testapp/ui/ConsentPromptScreen.kt`
- Android URI-scheme presentment: `samples/testapp/src/androidMain/kotlin/org/multipaz/testapp/TestAppUriSchemePresentmentActivity.kt`
- Android Digital Credentials presentment: `samples/testapp/src/androidMain/kotlin/org/multipaz/testapp/TestAppCredentialManagerPresentmentActivity.kt`
- iOS QR-based proximity presentment: `samples/SwiftTestApp/SwiftTestApp/Iso18013ProximityPresentmentScreen.swift`
- iOS Identity Document provider flow: `samples/SwiftTestApp/IdentityDocumentProviderExtension/DocumentProviderExtension.swift`

## Keep these distinctions clear

- OpenID4VP is a protocol, not a transport.
- DCQL is a query language, not a transport.
- QR and BLE are engagement or transport mechanisms depending on the flow.
- NFC credential presentation is currently Android-only in Multipaz.

## KMP Compose QR holder presentment

For a Compose holder app that already has a `DocumentStore`, `DocumentTypeRepository`, and `PresentmentSource`, prefer the `multipaz-compose` QR presentment API instead of hand-building QR payloads.

- Add `org.multipaz:multipaz-compose` aligned to the same Multipaz version as `org.multipaz:multipaz`.
- Use `org.multipaz.compose.presentment.MdocProximityQrPresentment` with the holder's existing `PresentmentSource`.
- Pass preselected documents only when you have verified the selected document can satisfy the verifier's expected `DocRequest`. If compatibility is uncertain, pass an empty list so Multipaz can choose any matching credential from the `DocumentStore`.
- Build `MdocProximityQrSettings(availableConnectionMethods, createTransportOptions)`: pass `availableConnectionMethods` as a `List<MdocConnectionMethod>` such as `MdocConnectionMethodBle(...)`, and `createTransportOptions` as a `MdocTransportOptions(...)`. These are the type's only two properties; do not invent others.
- Render the `uri` supplied to `showQrCode`; it should be an ISO 18013-5 `mdoc:` device engagement generated by Multipaz, not a credential identifier, credential text, or placeholder string.
- Let Multipaz run `Iso18013Presentment` and the consent prompt flow. Do not encode the credential itself into the QR code.
- Before showing a QR, verify the wallet has at least one `MdocCredential` whose `docType` and claims can satisfy the verifier's ISO mdoc request. A stored OpenID4VCI document may be SD-JWT-only, may use the expected mdoc `docType` but still miss requested claims, or may otherwise be incompatible with the verifier.
- For demos or unknown verifier requests, follow the Getting Started sample pattern: seed a local sample mDL with `DrivingLicense.getDocumentType().createMdocCredentialWithSampleData(...)` or equivalent known-good mdoc claims, and let QR presentment choose from the full `DocumentStore`.

## Validation

- Verify that the selected presentment mechanism exists in the current Multipaz version and sample set.
- For QR holder presentment, build and install the app, generate the QR code, scan it with a compatible mdoc verifier on another device, approve consent in the holder, and verify the reader receives and validates the credential. Treat this physical verifier pass as required; compilation and QR display alone are insufficient.
- Test cancellation while the QR is displayed or while waiting for the reader.
- For Android NFC, validate compile-time integration and note that runtime behavior usually needs physical hardware.
